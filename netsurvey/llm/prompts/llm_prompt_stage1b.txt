VI. SPECIFIC PROCESSING RULES & LOGIC (Apply to Stage 1B Data, using Stage 1A context):

*   **`moonid_associations` Logic (Strictly apply using ONLY extracted SITE_SPECIFIC_MOONID_DATA and Stage 1A data):**
    *   Reference SVIs, ARPs, Routes, and VLANs from the provided Stage 1A JSON output.
    *   **Rule A (IP-Based - Confidence 1.0):**
        *   SVI IP Match: SVI IP (from Stage 1A `ip_interfaces`) falls within MOONID's `ip_range_definition`. `resolution_method: 'SVI_IP_Match'`.
        *   ARP IP Match: ARP IP (from Stage 1A `arp_entries`) falls within MOONID's `ip_range_definition`. `resolution_method: 'ARP_IP_Match'`.
        *   Route Destination IP Match (Apply Route Specificity Filter from Stage 1A `routes`): `destination_prefix` matches MOONID's `ip_range_definition`. **CRITICAL FILTER:** Only if route's prefix is >= /20 (IPv4) or >= /48 (IPv6). Avoid if more direct SVI/ARP association exists for related MOONID. `resolution_method: 'Route_Destination_IP_Match'`.
    *   **Rule B (VLAN ID Match - Confidence 0.7 - ONLY if NO Rule A match for a MOONID):**
        *   Switch VLAN ID (from Stage 1A `vlans` list) matches MOONID's `vlan_id`. `resolution_method: 'VLAN_ID_Match'`.
        *   Qualify: Only if switch has active interfaces for this VLAN (check Stage 1A `interfaces` and `vlans[].ports_associated_text`).
        *   **Specific Handling for VLAN 1 (if `vlan_id` is 1):**
            *   If MOONID has `vlan_id: 1` AND `ip_range_definition` (L3 MOONID): Rule B association ONLY if L3 evidence of MOONID's `ip_range_definition` exists in Stage 1A ARP table or specific routes.
            *   If MOONID has `vlan_id: 1` but NO `ip_range_definition` (L2 MOONID): NO Rule B association.
            *   General VLAN 1 Caution: Exercise extreme caution.
    *   Exclusions: NO association by site match alone.
    *   MOONID Status Review: If association to non-'Operational'/'Being built' MOONID, add to `items_for_review`.
    *   General Principle: Prioritize strong, direct IP-based matches. Flag if MOONID associated is for a different site/building than the switch's metadata location (from Stage 1A `switch_details`).

*   **`discovered_unassigned_networks` Logic (MODIFIED: Use Stage 1A data; Stricter Exclusions):**
    *   List any IP network from Stage 1A (`ip_interfaces[].ip_address_with_prefix`, `arp_entries[].ip_address`, `routes[].destination_prefix`) that is NOT found within any `ip_range_definition` in the `SITE_SPECIFIC_MOONID_DATA`.
    *   **Primary Goal for this Field:** Identify potentially undocumented **site-specific operational networks** being actively used or routed on this device, beyond its basic default management or infrastructure IPs.
    *   **CRITICAL EXCLUSIONS (DO NOT ADD networks to this list if they fall under these categories, EVEN IF THEY ARE "USED" by the switch for its own operation unless that use is for site-specific user/application traffic not covered by MOONID data):**
        1.  IPs *solely* derived from LLDP/CDP neighbor management advertisements (i.e., from `neighbors[].remote_mgmt_address` in Stage 1A output).
        2.  Standard Infrastructure Networks: This includes default routes (`0.0.0.0/0`, `::/0`), loopback addresses (e.g., `127.0.0.0/8`), link-local addresses (e.g., `169.254.0.0/16`, `fe80::/10`), and broad standard multicast ranges unless they are verifiably used for site-specific multicast applications not defined in MOONID data.
        3.  **Common Vendor-Specific Default/Internal Networks:**
            *   These are networks known to be used by vendors for default management, internal operations, or initial setup.
            *   **Example:** D-Link's default management IP `factory-default-address` (often part of the `RFC 1918 supernets` or `vendor-default-range` range). If this switch is using `factory-default-address` (or a similar known default for its make) as its *own management IP* (e.g., on SVI Vlan1) and this IP is not part of any defined MOONID, **IT SHOULD BE EXCLUDED** from `discovered_unassigned_networks`. The purpose is not to rediscover the switch's own default management IP if it's not documented in a MOONID.
            *   Other examples might include unused Cisco default VLAN SVIs (e.g., VLANs 1002-1005) if they happen to get an IP but aren't used for actual site traffic.
        4.  Extremely Broad Private IP Ranges: Do not list entire broad private ranges like an RFC 1918 private supernet itself *unless* specific, narrower subnets *within* them (that are more specific than, say, a /20 for IPv4) are actively configured on the switch's interfaces for clear site-specific operational traffic AND these narrower subnets are NOT covered by any `ip_range_definition` in the `SITE_SPECIFIC_MOONID_DATA`. The focus is on operational networks, not just any potential address space the switch might be aware of via a broad route.
    *   `discovery_source_type`: 'SVI_Unmatched', 'ARP_Unmatched_IP', 'Route_Unmatched_Destination'.
    *   `discovery_context`: Specific IP/interface/route from Stage 1A data that led to this (e.g., "SVI Vlan1 IP: 192.0.2.23/24").
